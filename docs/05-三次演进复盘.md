# TaskMaster 的三次演进复盘

> 演进不是"功能越加越多"，而是每一次都换掉一个正在制造麻烦的结构性问题。本文按三次演进分别说明**动因、改了什么、付了什么代价、留下了什么**。

## 演进一：Servlet/JSP + SSM → Spring Boot 可执行 JAR

**动因**

原工程是传统 war 部署：`web.xml` 注册 Servlet 与 Filter，Spring 的 bean 与 MyBatis 的 SqlSessionFactory 全写在 XML 里，JSP 直接放在 `webapp` 下。这类工程有三个硬伤：容器依赖强（换 Tomcat 版本就可能 404）、启动慢（外部容器 + 应用两次装配）、配置不可读（一处 bean 改动要翻三个 XML）。

**改造内容**

- 引入 `spring-boot-starter-parent`，用 `SpringApplication.run()` 一个入口替代 `web.xml` + 容器外的装配流程；
- 删除全部 Spring XML，把数据源、MyBatis、模板引擎、会话超时收进 `application.yml`；
- 按环境拆出 `application-dev.yml` / `application-test.yml` / `application-prod.yml`，由 `spring.profiles.active` 切换，生产环境的库地址与口令改为 `${DB_URL}` 等环境变量注入；
- `packaging` 由 war 改为 jar，`spring-boot-maven-plugin` 的 `repackage` 生成可直接 `java -jar` 运行的可执行包。

**代价**

- 端口、上下文路径等原来写在 Tomcat 的 `server.xml` 里的东西，现在必须回到 yml，团队里习惯改容器配置的人需要重新适应；
- 可执行 JAR 体积变大（内嵌 Tomcat 与全部依赖），首次构建需要联网拉取 starter。

**遗留**

`mybatis.*` 前缀、`mapper/*.xml` 仍在，因为持久层还没换——这正好成为演进二的动因。

## 演进二：手写 SQL 的 MyBatis → MyBatis-Plus + 服务端校验 + 拦截器

**动因**

上一版每个实体都要写一套"接口方法 + XML 语句"：六条 CRUD 语句占掉一个 XML 文件，字段改名要同步改 `resultMap`、`Base_Column_List` 和实体三处；分页完全没做，列表页一次性查全表。

**改造内容（对应环节三、四、五）**

1. **持久层**：`mybatis-spring-boot-starter` 换成 `mybatis-plus-spring-boot3-starter`；`TaskDao`、`UserDao` 改为继承 `BaseMapper`，删掉手写的 6 个方法与两个 mapper XML；实体用 `@TableName` / `@TableId` / `@TableField` 声明映射；注册 `MybatisPlusInterceptor` + `PaginationInnerInterceptor(DbType.MYSQL)`，并设 `maxLimit=500`、`overflow=true`。
2. **查询表达**：条件查询改由 `LambdaQueryWrapper` 承担，`eq` / `like` / `and` / `orderBy` 都用方法名而不是字符串字段名，字段改名时编译期就能发现；分页用 `Page` + `selectPage`，`COUNT` 与 `LIMIT` 由插件追加。
3. **服务端校验**：引入 `spring-boot-starter-validation`，`Task` 上加 `@NotBlank` / `@Size`，登录表单抽出 `LoginForm` 并加 `@NotBlank` / `@Size`；控制器用 `@Valid` + `BindingResult`，校验不过直接回表单页，用 `th:errors` 在字段旁回显。
4. **统一异常出口**：新增 `GlobalExceptionHandler`，`BindException`、`IllegalArgumentException`、兜底 `Exception` 三类分别映射到同一张 `error.html`，页面上只给一句人话，堆栈只进日志。
5. **认证方式**：`AuthFilter`（Servlet 过滤器，前缀匹配白名单）退役，改为 `LoginInterceptor` + `WebConfig` 的 `excludePathPatterns` 白名单。拦截器在 DispatcherServlet 之内运行，能拿到 HandlerMethod、能走 Spring 的异常链，也不会再出现"过滤器先拦、拦截器又拦"的双重判断。

**代价（这也是报告要求讨论的部分）**

- **SQL 不可见**：`selectList(wrapper)` 看不到最终 SQL，只能靠 `log-impl=StdOutImpl` 打出来核对；复杂条件出错时，排查入口从"看 XML"变成"看日志 + 拼装过程"。
- **N+1 风险**：`BaseMapper` 只做单表，一旦要"任务 + 所属用户"，很容易在循环里逐条查，必须提醒自己改用一次关联查询或批量查询。
- **封装掩盖边界**：`updateById` 默认忽略 null 字段，看起来是便利，实际会让"把内容清空"这类操作失效——必须知道它的行为，否则会写出"改不掉"的 bug。
- **迁移成本外溢到测试**：持久层方法名全变，原有 34 个单测里大量 `verify(taskDao).selectByUserId(...)` 全部失效，测试必须同步重写，否则构建直接红。

**遗留**

模板只做了基础渲染，分页栏与错误回显是这一版新加的，还没在真机上跑过；跨机部署也没验证——这是演进三的动因。

## 演进三：单机 `mvn spring-boot:run` → 可执行 JAR 跨机部署

**动因**

前两版一直靠 IDEA 里点运行，环境（JDK、Maven、本地库口令）和开发机绑死，换一台机器就跑不起来，也无法回答"交付物到底是什么"。

**改造内容**

- 固化交付物：`target/task-servlet-demo.jar`，`java -jar` 单命令启动，不依赖外部 Tomcat；
- 固化环境契约：目标机只需 JDK 21 + MySQL 8；库地址、账号、口令通过 `DB_URL` / `DB_USERNAME` / `DB_PASSWORD` 注入，配置不再跟着代码走；
- 固化启动参数：`--spring.profiles.active=prod` 指定生产档，`--server.port` 允许改端口；
- 固化验证路径：`/login` 登录 → `/task` 分页 → 新增/编辑/删除 → 未登录直接访问 `/task` 应被重定向到 `/login`。

**代价**

- 环境变量成为新的"隐性依赖"：漏设 `DB_URL` 时启动会直接报数据源初始化失败，比原来"改配置文件"更难第一时间定位；
- 可执行 JAR 内嵌依赖，热更新不现实，每次改动都要重新打包上传；
- 会话默认存在内存，多实例部署时登录态不共享，需要引入 Redis 等外置存储（本实验为单实例，未处理）。

---

## 三次演进的共同结论

1. **每次演进都在减少"必须手写、必须同步维护"的重复面**：XML → yml、SQL → Wrapper、过滤器 → 拦截器，减少的都是双份维护点。
2. **代价从"显式"变成"隐式"**：省掉的样板代码并没有消失，而是转成了"必须知道框架默认行为"的知识负担（`updateById` 忽略 null、分页插件必须注册、JSqlParser 要单独引入）。
3. **测试是改造的安全绳，也是最容易被忽略的成本**：持久层换实现后，测试不改就等于没有测试；能一次改完并跑绿，靠的是测试先暴露了所有调用点。
